01 Überblick

Der Rezeptshop ist ein Web-Shop für Koch-/Rezeptprodukte, den wir zu fünft als Prüfungsleistung im Modul Web Engineering bauen. Das Besondere: Er ist keine einzige große Anwendung, sondern besteht aus mehreren kleinen, unabhängigen Programmen — einer Microservice-Architektur.

5 Backend-Services

Node.js + Express. Jeder kümmert sich um genau einen Bereich (Login, Produkte, Wunschlisten …).

2 Frontends

Reines Vanilla-JS: ein Portal für Kunden, eines für Admins. Kein React/Vue.

1 Datenbank

Eine gemeinsame PostgreSQL-DB, auf die alle Services zugreifen.

Warum Microservices?

Weil es die Prüfungsvorgabe ist — und weil man so übt, wie große Systeme in der Praxis gebaut werden. Jedes Teammitglied kann an „seinem" Service arbeiten, ohne den anderen in die Quere zu kommen. Der Preis dafür: Die Dienste müssen über das Netzwerk miteinander reden, und man muss den Überblick behalten. Genau dabei hilft diese Seite.

🚀 Das Wichtigste zuerst: Alles startet mit einem Befehl Wenn Docker installiert ist, reicht im Ordner rezeptshop/:
# Startet DB, alle 5 Services, beide Frontends + Testdaten
docker compose --profile dev up -d --build

Danach ist der Kunden-Shop unter localhost:8080 erreichbar. Details in Kapitel 8.

Wie hängt alles zusammen? Die Frontends im Browser rufen die Backend-Services direkt auf. Jeder Service, der eine Aktion absichern muss, fragt (1) den auth-service per /validate, ob das Login-Token gültig ist, und (2) den authorization-service per /check, ob der User die Aktion überhaupt darf. Alle Services lesen/schreiben in dieselbe postgres-Datenbank. auth und inventory verschicken Mails über mailpit.

06 Datenbank

Wir nutzen eine gemeinsame PostgreSQL-Datenbank mit 11 Tabellen. Sie wird beim ersten Start automatisch aus database/init.sql erzeugt.

Löschverhalten — was passiert bei „User löschen"?

Fremdschlüssel (Foreign Keys) regeln, was mit abhängigen Daten geschieht:

CASCADE (mitlöschen) Wird ein User gelöscht, verschwinden automatisch: sein cart (+ cart_items), seine verification_tokens, seine eigenen wishlists und seine permissions. Analog: Produkt löschen → aus allen Warenkörben & Wunschlisten entfernt.
SET NULL (Historie behalten) orders.user_id wird auf NULL gesetzt — die Bestellhistorie bleibt erhalten (wichtig fürs Geschäft). Ebenso beim Produkt löschen: orderpositions.product_id → NULL, aber der gekaufte Posten bleibt sichtbar.

Wichtige Constraints

  • carts.user_id UNIQUE → jeder User hat genau einen Warenkorb.
  • permissions UNIQUE(user_id, resource_type, resource_id) → pro Ressource nur eine Berechtigung je User (der /grant-Upsert überschreibt sie).
  • purchase_price in orderpositions speichert den Preis zum Kaufzeitpunkt — spätere Preisänderungen verfälschen alte Rechnungen nicht.
💡 Merksatz: Zeitvergleiche IMMER in SQL Unsere TIMESTAMP-Spalten haben keine Zeitzone; die DB rechnet in UTC, Node läuft evtl. in lokaler Zeit. Ein „ist der Token abgelaufen?"-Vergleich muss deshalb in SQL passieren (expires_at < NOW()), nie in JavaScript — sonst rechnet man um Stunden falsch.

07 Frontends

Prüfungsvorgabe: reines Vanilla JS/HTML/CSS, kein Framework. Beide Portale sind simple statische Webseiten, die per fetch mit den Backends reden.

🛒 user-portal · :8080

Seiten: index (Produkte+Suche), login (3 Tabs: Login / Registrieren / Magic-Link), warenkorb, bestellungen, wunschliste, magic & confirm (Landing-Pages vor dem Login, lesen ?token= aus der URL).

🛠️ admin-portal · :8081

Seiten: index/dashboard, login, produkte (anlegen/bearbeiten/löschen), benutzer (suchen/sperren/löschen). Zusätzlich requireAdmin(): prüft die Rolle frisch über /me.

Die zwei Helfer-Dateien

js/api.js — spricht mit den Backends

Enthält eine SERVICES-Map mit den Basis-URLs: auth :3001, inventory :3003, wishlist :3004, user :3005. Der authorization-service fehlt hier bewusst — das Frontend spricht ihn nie direkt an (er ist rein intern!). Die Funktion apiFetch hängt automatisch den Authorization: Bearer <token>-Header an. Kommt bei einem Aufruf mit Token ein 401 zurück, wird das Token gelöscht und der User auf login.html?session=expired umgeleitet.

js/auth.js — verwaltet das Login

Speichert das Token im localStorage (Schlüssel token). Funktionen: requireLogin() (schützt Seiten), logout(), currentUser() (holt & cached /me). Das admin-portal hat zusätzlich requireAdmin().

nginx macht hier fast nichts Beide Portale werden von einem Standard-nginx:alpine nur als statische Dateien ausgeliefert (der public/-Ordner ist read-only reingemountet). Kein Reverse-Proxy — deshalb ruft der Browser die Backends direkt auf, und deshalb brauchen wir CORS (siehe Lexikon).
